# ELASTIC 구현

ELASTIC은 캐시 일관성이 유지되는 통합 메모리 시스템에서 NVMe 오프로딩으로 배치 LLM 추론을 수행합니다. 공동 실행 기반인 **ELASTIC Engine**은 회전하는 레이어 슬롯, 블록 생성 순서를 따르는 저장 레이아웃, 도착 기반 어텐션, 라이트백을 연결합니다. KV/활성화 하이브리드 캐싱은 이 경로로 이동하는 바이트 수를 줄이고, 측정 기반 정책은 레이어마다 블록을 활성화 블록으로 저장할 비율인 활성화 비율을 정합니다.

이 문서는 구현의 데이터 흐름을 설명합니다. 설치와 실행 명령은 [사용법](USAGE_KO.md)에 있습니다.

## 1. 모델 초기화와 레이어 슬롯

[`StreamingModelLoader`](../elastic/vllm_runtime/streaming_loader.py)는 vLLM의 `elastic_streaming` 로드 형식을 등록합니다. 모델을 `meta` 장치에서 만들고 임베딩, 마지막 LayerNorm, 출력 헤드만 상주시킵니다. 디코더 레이어에는 영구 가중치 저장 공간을 두지 않습니다. 각 레이어 실행 직전에 [`WeightTable.bind_layer`](../elastic/runtime/weight_table.py)가 해당 파라미터를 로드된 슬롯의 가중치 버퍼 뷰에 연결합니다.

슬롯은 다음 네 버퍼를 함께 관리하는 논리적 단위입니다.

| 버퍼 | 담는 데이터 |
|---|---|
| 가중치 버퍼 (slot.weight) | 현재 레이어의 스테이징된 파라미터 |
| K 버퍼와 V 버퍼 (slot.k, slot.v) | 해당 레이어에서 읽거나 kv_gen으로 재계산한 K/V 블록 |
| 활성화 버퍼 (slot.act) | 읽은 활성화, 라이트백을 기다리는 활성화, 프리필 작업 데이터 |

버퍼는 정렬된 호스트 메모리를 할당하고 CUDA에 등록합니다. CPU의 I/O 경로와 GPU 텐서 뷰가 같은 메모리를 접근합니다. 이 경로는 캐시 일관성이 유지되는 UMA를 전제로 하며, 별도 호스트→디바이스 복사 단계를 구현하지 않습니다.

`StreamingModelLoader._compute_n_slots`는 사용자가 지정한 슬롯 메모리 예산과 최대 배치·시퀀스 길이로 슬롯 수 `n_slots`(논문의 N_slots, 식 9)를 정합니다. 활성화 버퍼는 선택한 활성화 비율과 관계없이 전체 용량을 예약합니다. 프레임워크, 임시 버퍼, 상주 파라미터와 OS가 사용할 메모리도 슬롯 메모리 예산 밖에 남겨야 합니다.

[`LayerSlotPool`](../elastic/vllm_runtime/layer_pool.py)은 단조 증가하는 **방문 번호(visit)**로 슬롯을 순환합니다.

```text
slot = visit % n_slots
```

방문은 한 레이어를 한 번 실행하는 단위이며 디코드 스텝과 배치가 바뀌어도 번호가 계속 증가합니다. 레이어 수가 슬롯 수로 나누어떨어지지 않을 때 `layer % n_slots`로 고정하면 잘못된 슬롯을 재사용하게 됩니다. 로더(`ReadRouter`)는 새 방문의 슬롯을 획득할 때 해당 레이어의 KV 캐시 연결도 바꾸고, 그 뒤에 읽기를 제출합니다.

## 2. 저장 레이아웃은 블록 생성 순서를 따른다

가중치 blob과 manifest는 [`stage_opt`](../elastic/cli/stage_opt.py)가 만듭니다. 실행 중 생성하는 캐시는 별도 blob이며 [`BlockKVLayout`과 `BlockKVStorage`](../elastic/runtime/block_kv_storage.py)가 관리합니다. 각 레이어의 파일 공간은 다음 세 블록 영역으로 이루어집니다.

```text
[ ACT_i: 활성화 블록 ][ K_i: KV 블록의 K ][ V_i: KV 블록의 V ]
```

저장 단위는 블록 전체입니다(vLLM PagedAttention의 `block_size` 토큰 블록). 시퀀스의 덜 찬 마지막 블록(가변 블록)도 빈 원소를 포함한 전체 블록으로 유지하고, 토큰이 추가될 때 같은 위치에 덮어씁니다. KV 블록은 토큰 우선 캐시 레이아웃을 유지하며, 활성화 블록은 어텐션 앞 LayerNorm을 통과한 뒤 Q/K/V 투영에 들어가기 전의 은닉 상태를 저장합니다.

레이어 안에서 배치 전체의 블록 하나를 전역 번호 `k`로 식별합니다. 시퀀스 수가 `N_seq`(`BlockKVLayout.n_seq`), 프롬프트 길이가 `S`, 시퀀스당 불변 블록 수가 `n = ⌊S/block_size⌋`(`BlockKVLayout.n_immutable`)일 때, 시퀀스 `seq`(0 ≤ `seq` < `N_seq`)의 블록 `j`(시퀀스 안의 블록 번호, 0부터)는 다음 번호를 갖습니다(논문 식 10–11).

| 블록 구간 | 전역 번호 `k` | 쓰기 동작 |
|---|---|---|
| 불변 블록 (`0 ≤ j < n`) | `k = seq · n + j` | 프리필에서 생성한 뒤 덮어쓰지 않음 |
| 가변 블록 (`j ≥ n`: 가변 프롬프트 블록과 디코드 블록) | `k = N_seq · n + (j − n) · N_seq + seq` | 디코드에서 시퀀스별 현재 블록을 덮어씀 |

이 순서에서는 한 디코드 스텝이 갱신하는 블록들이 전역 번호상 인접합니다. 형태 규칙을 적용하면 블록 영역(`ACT_i`, `K_i`, `V_i`) 각각에서도 조밀한 범위가 됩니다. 로더는 시퀀스별로 흩어진 위치를 따라가는 대신 각 블록 영역의 앞부분을 긴 연속 구간으로 읽을 수 있습니다.

[`labels.py`](../elastic/runtime/labels.py)는 블록의 형태(활성화 블록 또는 KV 블록)와 블록 영역 안의 조밀한 위치인 랭크를 정합니다. 파일 오프셋과 메모리 블록 위치는 모두 `BlockKVLayout`이 관리합니다. K 버퍼와 V 버퍼에서 0번 블록은 vLLM의 null 블록입니다. 활성화 블록은 1번 블록부터 놓이고 kv_gen이 재계산한 K/V를 그 자리에 쓰며, 직접 읽은 KV 블록은 실행 전체에서 그 레이어의 활성화 블록이 모두 놓인 다음의 고정 블록인 `mem_kv_base`부터 놓입니다. 저장·읽기·어텐션 메타데이터가 같은 매핑을 사용합니다.

`BlockKVStorage.ensure_exists`는 캐시 파일을 새로 만들거나 늘릴 때 `posix_fallocate`로 공간을 확보합니다. 논리적 블록 배치와 파일 공간 할당은 별개이며, 이 함수가 이미 존재하는 파일의 물리적 extent 배치를 복구하지는 않습니다.

## 3. 읽기는 사용할 수 있는 데이터를 순차적으로 알린다

로더인 [`ReadRouter`](../elastic/vllm_runtime/loader_thread.py)는 해제된 슬롯을 획득하고 레이어별 읽기를 다음 순서로 계획합니다.

1. 가중치 세그먼트 → 슬롯의 가중치 버퍼(slot.weight)
2. `ACT_i` 세그먼트 → 슬롯의 활성화 버퍼(slot.act). 읽은 활성화에 대한 kv_gen 실행 단위는 세그먼트와 따로 `ELASTIC_LOAD_CHUNK_TOKENS` 토큰마다 자름
3. `K_i`와 `V_i` 세그먼트 → 슬롯의 K 버퍼와 V 버퍼(slot.k, slot.v)

가중치가 모두 도착하면 로더가 슬롯을 게시합니다. 포워드 패스는 전체 컨텍스트를 기다리지 않고 레이어를 시작할 수 있습니다. 가중치 준비와 컨텍스트 블록 준비는 서로 다른 신호입니다.

블록은 어텐션에 사용할 수 있게 될 때 도착합니다. KV 블록은 K와 V가 모두 읽혔을 때 도착하며, 직접 읽는 KV 블록 구간은 K와 V의 읽기가 모두 완료된 뒤 게시됩니다. 활성화 블록은 kv_gen이 완료되었을 때 도착합니다. kv_gen은 별도 CUDA 스트림에서 실행됩니다. 실행 단위의 읽기와 해당 레이어의 가중치가 준비되면 [`kv_gen`](../elastic/kernels/kv_gen.py)(KV 재계산)이 레이어의 K/V 투영을 적용하고 결과를 K 버퍼와 V 버퍼의 목적지 블록에 바로 저장합니다. [`ACTLoader`](../elastic/vllm_runtime/act_loader.py)가 kv_gen 스트림을 소유합니다.

[`LayerArrival`](../elastic/vllm_runtime/layer_arrival.py)은 준비된 구간을 포워드 패스에 전달합니다. 항목에는 블록 영역 종류, 그 블록 영역 안의 시작 랭크, 블록 수가 들어가며 활성화 블록 항목에는 kv_gen 뒤 기록한 CUDA 이벤트도 포함됩니다. 텐서 데이터 자체를 복사해 넣지는 않습니다. 읽기가 모두 끝나고 kv_gen 실행 단위를 모두 실행 요청하면 로더가 피드를 닫습니다. 포워드 패스는 각 결과를 사용하기 전에 기록된 이벤트를 기다립니다.

## 4. 어텐션은 도착한 구간부터 소비한다

[`arrival_decode`](../elastic/vllm_runtime/arrival_attention.py)는 준비된 구간을 `ELASTIC_ARRIVAL_DRAIN_TOKENS` 토큰 분량의 도착 블록을 다루는 부분 어텐션 호출로 소비합니다. 이 양은 호출의 하한이자 상한이며(이보다 큰 도착 항목 하나는 나누지 않고 그대로 처리합니다), 레이어의 피드가 닫히면 남은 블록을 처리합니다. `BlockKVLayout`으로 블록 영역 안의 랭크를 시퀀스 행과 위치로 바꾸고, 포워드 패스의 스트림에서 해당 호출의 kv_gen 이벤트를 기다린 뒤 도착한 블록만 대상으로 어텐션을 계산합니다. 부분 출력과 log-sum-exp를 LSE 병합으로 질의 행별 누적 출력과 LSE(`running_o`, `running_lse`, FP32로 유지)에 병합합니다.

현재 블록(새 토큰을 받는 가변 블록)도 다시 읽습니다. 포워드 패스는 그 블록이 도착한 뒤 새 토큰의 K와 V를 추가하고 어텐션에 사용합니다. 활성화 블록이면 읽기와 kv_gen 뒤에 새 토큰의 은닉 상태도 활성화 버퍼에 추가합니다. 이 순서가 새 토큰을 뒤늦게 도착한 읽기가 덮어쓰는 일을 막습니다.

모든 시퀀스의 블록을 소비하면 병합한 어텐션 출력을 출력 투영과 FFN에 넘깁니다. 부분 어텐션을 시작하기 위해 레이어의 전체 컨텍스트 로드를 기다릴 필요는 없습니다.

프리필에는 다시 읽을 과거 컨텍스트가 없습니다. vLLM의 프리필 어텐션을 사용하고 이후 디코드가 읽을 캐시를 만듭니다. 큰 프리필은 지그재그 프리필로 GPU 배치들을 차례로 계산하여, 한 번 읽은 레이어 가중치를 GPU 배치들이 함께 씁니다. 불변 블록은 생성되는 대로 저장합니다. 지그재그 프리필과 캡처 콜백은 [`streaming_loader.py`](../elastic/vllm_runtime/streaming_loader.py)에 있습니다.

## 5. 쓰기 완료가 슬롯 재사용을 결정한다

라이트백인 [`WriteRouter`](../elastic/vllm_runtime/nvme_write_router.py)는 파일 구간과, 사용 중인 K 버퍼·V 버퍼·활성화 버퍼의 뷰를 받습니다. 별도 저장 버퍼로 복사하지 않으므로 쓰기가 끝날 때까지 원본 슬롯이 유효해야 합니다.

포워드 패스는 증가하는 티켓에 쓰기를 등록한 뒤, 데이터를 생성하는 연산 다음에 CUDA 스트림 마크를 넣습니다. GPU가 그 지점에 도달하면 [`StreamSignal`](../elastic/loader/nvme_loader.py)이 티켓 진행 상태를 게시하고 라이트백을 깨웁니다. 라이트백은 새로 제출 가능한 쓰기를 NVMe 엔진에 넘기고 완료를 거둬들입니다.

다음 세 조건을 모두 만족해야 슬롯을 재사용할 수 있습니다.

- 포워드 패스가 CPU 측 포워드 완료 표시(`forward_done_visit`)로 해당 방문을 인계했습니다.
- GPU가 해당 방문의 레이어 종료 티켓을 통과했습니다.
- 그 티켓까지 허용된 모든 쓰기가 완료되었습니다.

그때 라이트백이 그 방문의 슬롯을 해제하고(`release_tail`) 로더를 깨웁니다. Python 레이어 콜백이 반환된 것만으로는 원본 메모리를 해제할 수 없습니다. 디코드에서는 시퀀스별 현재 블록(스텝의 마지막 N_seq개 블록)을 저장하며, 프리필의 불변 블록은 더 일찍 저장할 수 있고 가변 프롬프트 블록은 레이어 종료 시 저장합니다.

## 6. NVMe 엔진 하나가 장치 I/O를 소유한다

[`NvmeEngine`](../elastic/loader/nvme_loader.py)은 Python에 읽기·쓰기 포트를 제공합니다. [`loader.c`](../native_loader/src/loader.c)의 C 스레드 하나가 두 포트의 공통 io_uring을 소유합니다. 읽기는 정해진 큐 깊이까지 보충하고, 제출이 허용된 쓰기 배치가 활성 상태이면 쓰기를 우선 처리합니다. 쓰기 요청의 결합·분할과 진행 중 쓰기 바이트에 대한 채움 제한도 이곳에서 수행합니다.

| 구성요소 | 담당 |
|---|---|
| 로더 (`ReadRouter`, 스레드 `elastic-head`) | 읽기 계획, 읽기 완료, kv_gen 실행 요청, 도착 게시 |
| 포워드 패스 (포워드 스레드) | 모델 실행, 부분 어텐션, 버퍼 갱신, 스트림 티켓 |
| 라이트백 (`WriteRouter`, 스레드 `elastic-tail`) | 준비된 저장 요청, 쓰기 완료, 슬롯 해제 |
| NVMe 엔진 (`nvme_engine`) | io_uring 제출·보충, 쓰기 구성, I/O 완료 전달 |

파일은 `O_DIRECT`로 접근하며 네이티브 제출 경로가 실제 direct-I/O 정렬 조건을 확인합니다. 짧은 전송의 나머지는 NVMe 엔진 안에서 처리합니다. Python은 완료된 항목 또는 오류를 받고, 결과를 확인한 뒤에 준비 상태나 해제 상태를 진행시킵니다. C 인터페이스는 [네이티브 로더 문서](../native_loader/README.md)에 있습니다.

## 7. 하이브리드 캐싱과 측정 기반 정책

위 실행 구조는 KV만 저장하는 실행과 하이브리드 실행이 함께 사용합니다. 지원하는 OPT 다중 헤드 배치에서 활성화(은닉 벡터) 하나의 바이트 수는 K/V 쌍의 절반입니다. 활성화 블록의 저장과 읽기는 저장장치 트래픽을 줄이는 대신 kv_gen 연산을 추가합니다. 손실 압축 코덱 대신 원래 은닉 상태를 사용하는 방식입니다.

활성화 비율 `alpha_curve`(레이어별 α_i)는 실행 동안 고정되며 하나의 스칼라 또는 레이어별 곡선으로 지정할 수 있습니다. 이 값에 따라 결정적인 블록 형태와 블록 영역 크기가 바뀌지만 슬롯·읽기·도착 소비·라이트백의 생명주기는 같습니다.

하이브리드 정책은 ELASTIC Engine을 위한 설정 단계입니다.

- [`elastic/cost`](../elastic/cost/)는 측정한 읽기 대역폭과 GPU 연산 비용(kv_gen, 어텐션, 레이어의 나머지 연산)에 설정된 지속 쓰기 속도(`ELASTIC_UNITS_WRITE_GBPS`, 기본 1.82 GB/s)를 결합해 비용 레코드를 만듭니다.
- [`from_units.py`](../elastic/policy/from_units.py)가 측정 조건을 확인하고 대상 워크로드와 슬롯 메모리 예산에 맞는 비용으로 바꿉니다.
- [`solver.py`](../elastic/policy/solver.py)가 디스크와 GPU의 예상 시간(`T_NVMe^i`와 `T_comp^i`) 및 유한한 슬롯 메모리가 허용하는 앞섬 시간(`C_mem`)을 바탕으로 레이어별 활성화 비율을 정합니다.

컨텍스트 길이, kv_gen 실행 단위의 크기, 부분 어텐션 호출의 양을 바꾸면 그 조건에 맞는 측정이 필요합니다. 런타임은 결과 곡선을 읽으며, 토큰마다 비율을 동적으로 바꾸지 않습니다. 명령과 출력 파일은 [사용법](USAGE_KO.md)에서 설명합니다.

## 통합 범위

이 문서가 설명하는 경로는 pre-norm OPT, FP16, Linux io_uring, NVMe, 캐시 일관성이 유지되는 CUDA UMA와 저장소의 [vLLM 패치](../patches/vllm-elastic.patch)를 사용합니다. 패치는 레이어 콜백, KV 캐시 할당·연결, 도착 기반 어텐션 진입점, 프리필과 runner 연결을 제공합니다. 방문마다 디코더 파라미터를 다시 연결하므로 eager 실행이 필요합니다. 현재 모델 로더(`StreamingModelLoader`)는 CUDA 그래프 실행, 양자화 KV 캐시, post-norm OPT를 거부합니다.
